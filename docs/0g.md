# 0G — what we built, where it lives, and what we did not build

**Track:** Best AI Product on 0G · ETHGlobal Lisbon 2026 · 100% testnet.

This document is the 0G-specific reading of the project. It is written to be checked: every claim
points at a file, a gate you can run, or a public record you can open without asking us for
anything. The last two sections are the honest inverse — what the track invites that we did not
ship, with an implementation sketch for each gap, and the sentences we refuse to say.

The one-line summary: **0G is the compute, and the client's intent is carried through it.** The
deliverable Alice buys is produced inside a 0G Sealed Inference enclave, so neither Bob — the
party being paid — nor the infrastructure ever sees her brief. The output comes back signed by
the TEE, and Alice's signed intent commitment rides *inside* the body that signature covers.

> **0G proves the computation happened in a TEE. We prove it was the right computation.**

## 2. Where 0G sits in the job

Four networks, each doing exactly one thing:
**Base = the verdict · Hedera = the money and the timeline · The Graph = the read layer · 0G = the compute.**

```
 1. DISCOVER    Alice queries a subgraph by skill; her brain picks Bob.        (The Graph)

 2. INTENT      intentHash = keccak256(briefHash, dataHash, constraints,
                price, nonce), signed EIP-712. This commitment is the spine.

 3. ENCRYPT     brief + data are ECIES-encrypted to the BINDING's key.
                Bob — the party being paid — cannot read them.

 4. 402         Bob quotes and does no work until an authorisation exists.     (Hedera / Base)

 5. RECOMPUTE   The binding decrypts, rebuilds the hash from what it actually
                received, and compares it to what Alice signed → `match`.

 6. SEALED      The prompt — with the intent commitment pinned at the TOP —
    INFERENCE   goes to 0G Sealed Inference. The model runs where neither Bob  (0G)
                nor the infra sees the data. The answer echoes the commitment.

 7. TEE SIG     The enclave's signature is fetched and verified in TWO steps    (0G)
                (§3). `ogVerified` is never silently true.

 8. ARCHIVE     The deliverable is AES-256-GCM encrypted and uploaded to        (0G)
                0G Storage. Public address, private contents. (opt-in, §5)

 9. VERDICT     Verifier.sol recovers the binding seal + Alice's EIP-712
                intent and requires match == true → JobVerified.               (Base)

10. SETTLE      Payment releases only after that event.                        (Hedera / Base)
```

## 3. What the TEE signature actually covers — measured, not assumed

This is the part we are proudest of, and it started as a bug hunt.

The obvious reading of "the TEE signs the output" is that the signed message *is* the answer text.
It is not. We hashed every candidate against the signature's message and found only one match. The
signed message is a **pipe-free, colon-joined tuple**:

```
"<h1>:<sha256(RAW response body)>:<ProviderType>:<ProviderIdentity>:<h3>"
```

So the answer **is** covered — as the **fingerprint of the body that contains it**, not as plain
text. Same protection against tampering; a different sentence. We use the accurate one everywhere,
including on the dashboard.

Three consequences, all of them load-bearing:

**(a) Verification takes two steps, and both are required.**

```ts
// packages/shared/src/compute-0g.ts
ogSigner = verifyMessage(sig.text, sig.signature);          // (a) a genuine TEE signed SOMETHING
const digest = createHash('sha256').update(rawResponseText).digest('hex');
const coversThisResponse = sig.text.split(':').includes(digest);  // (b) it signed OUR response
ogVerified = signerOk && coversThisResponse;
```

If (a) alone were enough, an attacker could hand us a **valid** TEE signature belonging to a
different request and call it proof. (b) closes that door — and when the signature is valid but
the digest does not match, the code *throws* rather than degrading quietly, because that
combination is precisely the attack.

**(b) The raw bytes matter.** A `JSON.parse` → `JSON.stringify` round-trip depends on key order and
would break silently the day the provider reorders its fields. `rawResponseText` is kept and hashed
as received. `pnpm gate:P0-B` asserts that a one-byte change drops out of the tuple.

**(c) `chatID` is not `completion.id`.** The signature endpoint recognises the id in the
**`ZG-Res-Key` response header**; the completion's own `id` returns `chat_id_not_found`.

### TeeML is necessary but not sufficient

`compute-0g.ts` refuses a provider unless **both** hold:

- `verifiability === 'TeeML'` — TeeTLS does not carry the "the operator cannot see the data" claim,
  so we do not accept it;
- `teeSignerAcknowledged === true` — when false, `teeSignerAddress` is the provider's *own claim*
  and the contract owner has not vouched for it.

There is also a `resolveExpectedSigner` step: for a separated, non-centralized provider the model
runs in its own enclave and signs there (`TargetTeeAddress`), while a centralized provider's broker
TEE signs. We read `additionalInfo` and pick the right expected address rather than assuming one.

## 4. The intent binding — what 0G's enclave attests, and what it does not

### The gap we are closing

A TEE proves that *a* computation happened inside it. It does not prove the computation was **the
job the client ordered**. Bob can answer a cheaper question, a stale question, or another client's
question, and every cryptographic check still passes. The gap is invisible precisely because every
individual component is sound.

### What we do

Alice's `intentHash` is pinned at the **very top** of the prompt, and the model is asked to copy it
back character for character:

```
ORDER-ID: 0x…64 hex…

Begin your reply with exactly this line, copied character for character:
ORDER-ID: 0x…64 hex…

Then answer the brief below.
```

Therefore:

```
Alice signs intentHash  →  it goes to the TOP of the prompt
                        →  the model copies it verbatim into its answer
                        →  0G's TEE signs sha256(response body) — a body CONTAINING that answer
⇒ a genuine 0G enclave has attested: "a response carrying THIS intentHash was produced in here"
```

Bob cannot forge that chain on his own machine: the first link comes from 0G hardware.

**Measured, not hoped for.** `scripts/og-probe-echo.ts` runs five rounds with a *different* hash
each time (so the model cannot memorise one) and requires an exact match — in a 64-digit hex value
a one-character shift breaks the binding, and "approximately right" is not a category. Result:
**5/5**. It is re-checked in `pnpm gate:P3-B`, and it held again in a *separate* set of five full
end-to-end jobs: `intentEchoed` is `true` in all five entries of `fixtures/latency/P0-G.json`, as is
`ogVerified`.

**Top of the prompt, on purpose.** At the end, a long answer risks `max_tokens` truncation and the
model losing track of the instruction after a long generation. At the top it held 5/5.

**The check does not trust the backend.** `runBinding` looks for the hash in the **raw output
itself** — a compute backend could simply *claim* it inserted the commitment:

```ts
// packages/bob-binding/src/binding.ts
const intentEchoed = computed.output.includes(claimedIntentHash);
```

### The enclave does not lie, it reports

Under fraud the model is **still called** and the body is **still signed**, with `match: false`
inside it. An enclave that refused to answer would be an enclave that could be silenced; one that
signs an honest "no" is one the contract can act on. `Verifier.sol` then rejects with
`MatchFalse`, no `JobVerified` is emitted, and settlement — which re-reads that receipt from Base
before releasing anything — never fires.

### Why this is Level 0, and what Level 1 would add

**We had no TDX host.** The design wanted Bob's own attested Tapp doing the recompute, so the
attestation would read `codeDigest + inputHash + outputHash`. 0G does not host Tapp execution for
us and we have no TDX machine, so **the recompute runs as ordinary, unattested code.** Rather than
fake an attestation, we moved *one end* of the binding inside 0G's real enclave — that is the echo
above.

The honest delta, one sentence wide: **with our own attested enclave, the `match` check itself
would sit inside the seal and a third party could trust it without trusting us. Today the client
can verify it independently; a stranger cannot yet.** Nothing else in the pipeline changes.

`attestation: 'none'` and `imageHash: null` therefore stay in the code, in the HCS timeline and in
the UI until that changes. We would rather ship a true `null` than a comfortable string.

**Not verifiable on-chain, by design:** the TEE signs the *digest* of the response body, so
checking the echo requires the body itself. `Verifier.sol` verifies `match`; the echo is the
independently-verifiable strengthening for anyone holding the response — Alice, and anyone who
downloads the proof bundle. No contract change, no redeploy.

## 5. 0G Storage — the archive that does not leak

Enabled with `OG_STORAGE=1` (opt-in: every job costs a fee plus gas, and a run that did not ask
for storage does not get billed for it; when it is off we report "no archive" rather than
inventing a root hash).

**What it buys, precisely:** the on-chain `outputHash` stops being the hash of something only Bob
happens to still have in memory and becomes the hash of something **anyone can fetch**. The verdict
was already public; the artefact it refers to now is too.

**What it does not buy:** any new guarantee about the work. A blob on 0G Storage is not more *true*
than the same blob on Bob's disk — it is more **available**. We say it that way.

The design decisions worth naming:

- **Encryption is ours, not the SDK's.** AES-256-GCM, a fresh key per blob generated inside the
  binding. The gate has to prove the bytes coming back hash to the **same `outputHash` that went on
  chain**, which requires knowing exactly which bytes were sealed — so the plaintext is *exactly*
  the deliverable: no wrapper object, no re-serialisation, no key ordering to depend on.
- **The key travels to Alice only.** It rides inside the ECIES result envelope and is deliberately
  **not** part of `BindingResponse`, so Bob's outer layer never holds it. The network sees
  ciphertext; anyone can download the blob; only Alice can read it. The key is also excluded from
  `DemoReport` — those reports are committed to git, and a key there would undo the whole boundary.
- **The root hash is not folded into the sealed body**, and that is deliberate rather than lazy:
  the body is the four fields `Verifier.sol` rebuilds, and a fifth would mean a redeploy. It is
  also unnecessary — `outputHash` **is** sealed and it is the keccak256 of the very bytes stored,
  so swapping the blob does not go unnoticed, it fails the hash. The seal covers the **content**;
  the root hash is only the address it lives at.
- **A failed upload does not fail the job.** Storage is the bonus leg; the hero flow survives it
  being down. The reason is reported rather than swallowed — an absent archive and a broken one
  must not look the same.

`pnpm gate:P3-E` splits the claim into three and checks each: the blob is **fetchable** from
storage nodes that have never seen us, **readable** with Alice's key and *only* that key (a wrong
key throws on the GCM tag rather than returning plausible garbage), and **the same** — its
keccak256 equals the `outputHash` the contract ruled on.

## 6. 0G Compute as the agents' brain (optional)

The agents make real decisions: who to hire, whether to approve the quoted price, and whether the
delivered work was any good. Those decisions run behind an interface with three interchangeable
backends — and one of them is **0G Compute** (`REASONING_BACKEND=0g`,
`packages/shared/src/reasoning-0g.ts`), driving the same `ComputeBackend` as the deliverable.

Two labels, kept separate on purpose, and both shown in the dashboard:

- **`computeProvider`** — who *produced the deliverable*. Always the 0G enclave.
- **`reasoningProvider`** — who *chose*. Configurable; the gates run the deterministic `policy`
  brain, because a gate whose outcome depends on a model's mood is not a gate.

The separation is not cosmetic. **The model being sold is not the model deciding:** reasoning never
produces output that anything signs. The brain never sees a private key (the spawned process's
environment is scrubbed). And it can only ever *narrow* a guarantee — it must name a candidate that
was actually offered, its price approval is ANDed with a hard ceiling no prompt can move, and it
can reject work the cryptography accepted but can never accept work whose commitment failed.

> A confused — or prompt-injected — agent can refuse to trade. It cannot overpay, invent a
> counterparty, or make an invalid job verify.

## 8. Reproducing it

```bash
pnpm install
cp .env.example .env      # fill in: OG_RPC_URL, OG_PRIVATE_KEY, OG_PROVIDER_ADDRESS
pnpm build

pnpm gate:P0-A            # env + balances: every account funded, and a missing field says which
pnpm gate:P0-B            # the hero gate — TeeML listing, the signature verified against OUR OWN
                          # code rather than the SDK's, WHAT the tuple covers, the one-byte test,
                          # fixture replay with no network, and the single-call latency
pnpm gate:P3-B            # binding + real Sealed Inference: honest run verifies, fraud is signed honestly
pnpm gate:P3-D            # the four fraud modes, each rejected on chain with its own code
OG_STORAGE=1 pnpm gate:P3-E   # encrypted archive: fetchable, readable, and the same bytes

npx tsx scripts/og-probe-echo.ts  # the 5/5 echo experiment, from scratch
npx tsx scripts/og-budget.ts      # what the faucet buys, measured against the live tariff
```

A full job, and the fraud path:

```bash
pnpm demo:base                            # honest run  → JobVerified
pnpm demo:base -- --fraud substitute      # Bob answers a different job → MatchFalse, nothing settles
OG_STORAGE=1 pnpm demo:base               # …and archive the deliverable on 0G Storage

pnpm --filter @ca/web dev                 # the demo dApp on :3000
```

**Iterating without burning faucet credit:** `MOCK_0G=1` replays the recorded responses in
`fixtures/og/` — same bytes, same signature, same verification path. Every real call made during
development was recorded on the way through (`compute-fixture.ts`), which is why the gates are
runnable by anyone who clones this repo with no 0G balance at all.

Faucet: [faucet.0g.ai](https://faucet.0g.ai). The compute ledger needs a minimum balance to open
an account that the daily faucet grant alone does not reach — that blocked us for a day and is
worth knowing before you plan around it.

## 10. What we did NOT build, and how we would

Written so a judge does not have to guess, and so whoever picks this up next has a starting point.
Ordered by value per hour of work.

### 10.1 The binding inside our own attested enclave (Level 1)

**What is missing:** the recompute that decides `match` runs on an ordinary host. This is the one
real gap in the thesis and §4 states it plainly.

**How:** a TDX host (a hosted TDX node, or cloud credits) running the 0G `agent-wrapper` Tapp with
`packages/bob-binding` as the custom agent — the package is already factored to be exactly that
(hashing plus orchestration, light enough for any CPU TEE, and its network egress is restricted to
0G on purpose so the `imageHash` claim stays clean). The seal-key path is *already implemented and
proven by simulation*: the preimage
`keccak256("agentId|sealId|timestamp|hex(sha256(body))")`, the 64-byte R‖S signature with `v`
discarded and brute-forced off-chain, and `setEnclaveSigner` kept owner-mutable for the demo
window because infra restarts rotate the key. `scripts/recover.js` recovers the right signer today.
What is missing is a machine, not code. **Then:** verify `imageHash == hash(our published image)`
at setup — that check is what makes "the enclave ran *our* code" true.
**Estimate:** hours, once a host exists.

### 10.2 Agentic ID

**What is missing:** the agents' identity is ERC-8004 on Base Sepolia. Nothing is minted on 0G.

**How:** mint Bob as an Agentic ID and **derive** it from the existing ERC-8004 identity rather
than minting a second, unrelated one — this has to be a bridge, not a competing registry, and the
README must say so. The natural payload is the thing we already produce: the encrypted deliverable
archive on 0G Storage becomes the agent's persistent memory, addressed by its Agentic ID.
**Estimate:** half a day. **Best value of anything on this list**, because it converts work we have
already done into the track's own vocabulary.

### 10.3 A contract on 0G Chain

**What is missing:** `Verifier.sol` lives on Base Sepolia. On 0G Chain we open a compute ledger,
pay providers and register storage uploads — real transactions, but no contract of ours.

**Why:** one source of truth per layer, chosen deliberately. The verdict lives where the ERC-8004
registry and the subgraph already are; duplicating it on a second chain would make a track look
bigger without making anything more true.

**How, if 0G wants the verdict local:** `Verifier.sol` has no Base-specific dependency — it is
signature recovery plus an event. Deploying the same bytecode to 0G Galileo and pointing the
settlement guard at it is a config change plus a subgraph data source. The honest version is to
move it, not to mirror it.

### 10.4 Persistent, evolving encrypted memory

**What is missing:** we archive **one deliverable per job**. The track's idea is an agent whose
memory *accumulates* on 0G Storage across jobs.

**How:** key a manifest blob by `agentId`, append each job's `{intentHash, outputHash, rootHash}`
and re-upload; the root hash of the manifest becomes the agent's memory pointer (and, with 10.2,
the Agentic ID's payload). Retrieval then feeds prior context into the prompt. The encryption,
upload, download and hash-equality machinery all exist already — what is missing is the append
loop and a pointer that survives restarts. **Estimate:** 3–4 h.

### 10.5 `intentEchoed` is computed but not surfaced

**What is broken:** the echo is our strongest 0G-specific claim. It is checked in
`binding.ts`, carried in the sealed body's schema and recorded per-run in the latency fixture — but
it is **not** a field on `DemoReport` and no dashboard panel shows it. A judge sees
"0G TEE signature: verified" (which anyone can show) and not the line that distinguishes us.

**How:** add `intentEchoed` to `DemoReport` in `packages/demo/src/index.ts` (it is already on the
binding result), render it in `VerifyPanel` next to the TEE-signature field, and include it in the
proof bundle. **Estimate:** ~1 h. Do this before recording the video.

### 10.6 Smaller ones

- **Storage is off by default, and it shows.** `OG_STORAGE` is not set in the demo environment, so
  the archive — which works, with real root hashes and transactions — is invisible unless someone
  opts in. It is *also* why the archived roots we can point at came from fraud runs
  (`fixtures/runs/{forge,substitute,selfintent}.json`) rather than from the recorded honest run:
  storage happened to be on for those. Re-record the honest run with `OG_STORAGE=1` and link its
  root hash from the evidence panel.
- **A decentralized provider.** We pinned one that reports `centralized / aliyun` (§11). Re-running
  provider selection against a decentralized TeeML provider is a config change; we pinned this one
  for stability during the build.
- **`processResponse` for billing.** We verify the signature ourselves (§3) because we needed to
  know *what* it covers. The SDK's own `processResponse` also settles the ledger entry; we call the
  signature endpoint directly and let settlement stay lazy.
- **Streaming.** Calls are single-shot. With inference at 80% of end-to-end latency, streaming the
  answer would improve the *perceived* number, though not the verifiable one — the signature covers
  a complete body.

## 11. Honest boundaries specific to 0G

Say these before a judge asks. Every one of them is on the dashboard already.

- **We did not build the TEE.** 0G did. What we added is the binding of intent to it.
- **The 0G signature does not cover the answer *text*.** It covers the answer's **fingerprint** —
  a colon-joined tuple containing sha256 of the raw response body. Same tamper guarantee, different
  sentence, and we use the accurate one.
- **The enclave did not verify that the job matches the order.** It attests that a response
  carrying this `intentHash` was produced inside it. Whether that hash really is the hash of *this*
  brief and data is checked by **unattested** code — the model copies the value, it does not
  validate it. The accurate sentence: *0G attests the compute and carries the intent through it;
  the match check is client-verifiable, not yet third-party-verifiable.*
- **One TEE, not two.** Bob's binding runs on an ordinary host because no TDX machine was available
  to us. `attestation: 'none'` and `imageHash: null` stay honest in the code and in the UI.
- **Not "decentralized compute"** — for the provider we pinned. `0xa48f…7836` reports
  `ProviderType: centralized`, `ProviderIdentity: aliyun`. The TEE seal is real (dstack / Intel
  TDX); the operator is a single cloud.
