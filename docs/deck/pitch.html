A seal that never looked at the document.

You pay a translator for a forty-page contract. A file comes back under a notary's seal: “this document was produced in my office.” The seal is real. But the notary never read what was translated — so if he seals some other document he already had, the seal still checks out.

That is exactly where agents are. Run something cheaper, sign the output, and the signature verifies. The attestation is real. The job is wrong.

This is not a flaw in TEEs. A TEE is answering the question it was asked — nobody was asking the other one.

The gate · Base Verifier.sol rebuilds the signed body from the struct fields — no JSON parsing, no trusting what Bob claims he signed — recovers both signatures, and requires match == true. The buyer never trusts the seller's arithmetic and the contract never trusts the seller's JSON. Both recompute from primary inputs.

0G proves the computation happened. We make it prove which one.

Sealed
The model runs in a Sealed Inference enclave via the broker: pin a TeeML provider, fetch request headers, POST /chat/completions, verify with processResponse. The party being paid never sees the brief.
Verified
We check the TEE signature ourselves, and we require teeSignerAcknowledged — without it the signer address is the provider's own claim and nobody has vouched for it. The chatID comes from the ZG-Res-Key header, not the completion id.
Carried
The buyer's commitment is written to the top of the prompt and the model copies it back verbatim, so the signature 0G's hardware produces covers a body that contains her intent. Measured 5/5. Bob cannot manufacture that on his own machine.
Archived
The deliverable goes to 0G Storage encrypted client-side. Anyone can fetch it by root hash; only the buyer holds the key.

Two things we say out loud: the signature covers the body's fingerprint, not its text — so we hash the raw response bytes, never a re-serialised copy. And the pinned provider reports ProviderType: centralized · aliyun: the seal is real, the operator is one cloud.

Two sources
One subgraph indexes both the public ERC-8004 registry (who exists, what skills, which endpoint, which pubkey) and our own JobVerified / JobRejected events (what actually happened). Joining those two is what makes discovery mean something.
Discovery
Alice queries where: { skills_contains: [skill] } and ranks by verified deliveries. She is never handed an address — the read layer is how she learns Bob exists at all.
Unwritable
There is no review endpoint and no self-report. The only thing that increments the counter is a contract event. You cannot buy the score; you can only earn it.
Visible
Rejected attempts sit on the same record as the successes, so a cheat stays visible exactly where the next hiring decision is made.

Say the shape of it before anyone catches it: 28 of the 31 indexed agents are strangers — but only three registrants fill the optional skills field in, so a skill query returns a short list. The read layer is what makes a sparse public registry usable at all.

The proof is the stage that is missing.

Authorised
Bob's endpoint answers 402 with a price and does no work. Alice signs an x402 authorisation through the blocky402 facilitator — and the money stays hers.
Then paid
The verify/settle split is the whole point: Bob submits the authorisation only after the contract emits JobVerified, and the settlement guard re-reads that receipt before releasing anything.
On the topic
Every stage is committed to a Consensus Service topic. An honest run ends … → OUTPUT_COMMIT → SETTLED. A fraud run stops at OUTPUT_COMMIT. The absent stage is the argument, timestamped on a ledger that is not ours to edit.
Delegated
The payment key lives behind a signer boundary. The agent — and the model driving it — is never given it. That boundary is tested, not just documented.

Unprompted, because it is the honest half: every message is a commitment, never content — the brief never touches Hedera. This rail buys autonomy and an ordered public record, not privacy. The unlinkable recipient is on the Base run.

The one place a job becomes true or false.

Rebuilt
The contract reconstructs the signed body as abi.encode(intentHash, outputHash, match, ogSigHash) from the struct fields. It never parses Bob's JSON and never trusts an intent + signature pair he supplies.
Two recoveries
Bob's binding signature must recover to the registered signer for that agentId; Alice's EIP-712 signature must recover to intent.client, and that client must be registered. Either failure is its own code.
One flag
Then, and only then, require(match). Replay is blocked by a verified[intentHash] map and staleness by a deadline.
Two doors
verifyJob reverts and is what settlement calls. verifyJobLenient emits the rejection code instead of reverting — that is the fraud button, so a refusal is a permanent public event rather than a failed transaction nobody can read.

On the Base run the payout also lands on a fresh ERC-5564 stealth address, derived per job: it does not name the seller, and two of his jobs cannot be linked by their payouts.

Two signatures, and neither one is where you would guess.

0G · attested hardware

Proves a genuine enclave produced the body

// EIP-191 personal_sign, NOT over the answer text
"<h1>:<sha256(raw body)>
     :<ProviderType>:<ProviderIdentity>:<h3>"

The answer is covered as the fingerprint of the body containing it — so a one-byte change drops out of the tuple. Hash the raw response bytes; a JSON round-trip breaks silently the day the provider reorders a field.

Bob's binding · unattested host

Proves his code checked match and bound intent to output

// keccak256 of a pipe-joined string, NO prefix
"agentId|sealId|timestamp|hex(sha256(body))"
body = abi.encode(intentHash, outputHash,
                  match, ogSigHash)

The signer is an ephemeral seal key registered per run, never Bob's agentId. This one is honest but not attested — see slide 15.

Every crypto boundary here has its own unit test, because all three traps above fail silently: a wrong prefix, a swapped hash primitive or a dropped recovery byte all produce a valid-looking address that simply is not the right one.
